# Bug 修复复测方法论

研发声明"已修复"后的标准复测流程与关键陷阱规避。

## 何时使用

- 研发说某 Bug 已修复，需要复测验证并更新用例/报告
- 修复部署进行中或部分部署（多副本滚动），需要判断验证结果有效性
- 此前上报的 Bug 需要重新确认现状（含撤销误判）

## 框架接入

先遵循框架根目录的 `AGENTS.md`，再读取
`giteerepo-test-delivery/SKILL.md`。从当前任务对应的 `workspace/` 版本目录
读取需求、原用例和既有结论；把复测脚本放在 `test_run/_scripts/`，把基线快照、
命令证据和恢复证明放在当前任务的 `test_run/evidence/`，把复测报告放在
`test_run/results/`。

行为复测前必须从 `environment_rule/` 解析当前环境和安全边界。不得用
`environment/`、`tools/` 或 archive 中的旧信息推断版本、目标或权限。若复测
需要补充测试用例或测试点，遵循 `giteerepo-test-delivery` 的输出规范。

## 核心规则

### 规则 1：复测三步确认（缺一不可）

```
① 代码确认：读取获准的代码版本或提交范围 → git log 找修复提交 → git show 看具体 diff
   （确认修复改了什么、覆盖哪个路径、是否完整）
② 部署确认：环境版本号（rev）+ 服务实例启动时间 + 修复提交时间对照
   （修复提交晚于部署则验证无效；多副本时新旧实例并存）
③ 行为验证：环境实测（API 直写/UI 操作）+ 回读断言
```

**优先级**：代码不完整 → 直接判"修复不完整"；代码完整但行为未变 → 先怀疑部署未生效（再查部署），排除后才判修复无效。

代码确认只使用获授权的只读工作区或远端引用。需要获取更新时可以执行只读
`fetch`，但不得为了复测而 checkout、merge、reset 或修改业务源码。

### 规则 2：基线残留误判陷阱（最重要）

**写操作（PUT/编辑）验证"是否写入"时，必须用基线无配置的对象，且用"传入值 vs 回读值"对比判断**：

| 判据 | 可靠性 |
|---|---|
| 回读值非空 → "已写入" | **不可靠**：可能是基线残留（此前测试或他人写入的旧值） |
| 传入值 X（≠基线）→ 回读=X | 可靠：确实写入（Bug 仍在） |
| 传入值 X（≠基线）→ 回读=基线值 | 可靠：未写入（修复生效） |

**最佳判据**：传一个与基线**明确不同**的值。回读仍等于基线 → PUT 未生效（修复）。
**反例实录**：远程仓库基线已有 masterSwitch=true，PUT 传 true 后回读 true 被误判"写入成功"；后经比对另一字段（传 false 回读 true=基线值）才确认 PUT 根本未生效——误判方向是把"已修复"判成"未修复"。

清理辅助判据：对基线已有配置的对象，PUT null/false 常常**无法清除**（需要专门删除接口）——不能以"关不掉"推断"修复无效"。

### 规则 3：HTTP 状态语义区分

| 状态 | 含义 | 判定 |
|---|---|---|
| 200 + 非法值入库 | 静默接受 | 未修复 |
| 400 + 明确校验提示 | 正确拦截 | 已修复（理想方式） |
| 值被修正后保存（如 -1→0.01） | 静默修正 | 按产品口径：能阻挡非法输入即为正确处理 |
| **500 系统错误** | **异常**——不是修复！ | 必须查日志定位异常点：请求可能**未走到修复代码**就因其他环节失败（如前置校验拉取外部 URL 失败），此时该路径的"未写入"不能归功于修复 |

### 规则 4：多环境交叉验证

目标环境部署中断/滚动未完成时：
- 用另一已部署同版本环境交叉确认行为
- **注意两环境基线差异**（对象配置/数据状态不同可能导致现象不同——见规则 2）
- 环境恢复能力不同：共享环境需完整恢复，独立环境记录改动即可
- 交叉结论仍需在目标环境最终复测确认

### 规则 5：修复完整性检查（不只看"改了"要看"改全了"）

- 校验类修复：逐字段比对（如只校验 A 字段负值、B 字段负值仍放行 → 部分修复）
- 类型判断类修复：确认修复点覆盖**所有入口路径**（创建/编辑/导入等）
- 一处修复多分支使用时：确认所有分支的调用链都经过修复点

### 规则 6：验证后交付物更新

- Excel：红→绿需附复测证据（日期+验证方式+关键断言值）
- 报告：Bug 清单状态更新（已修复/未修复/部分修复）+ 修复提交号 + 复测结论表
- **误判修正必须透明**：记录"此前结论 X，修正为 Y，修正依据 Z"（含此前误判原因）——不悄悄改结论
- 环境恢复声明（基线恢复+回读确认）

## 执行流程

```
1. 确认修复提交（fetch → log → show diff，判断修复完整性）
2. 确认部署状态（版本号+实例启动时间 vs 提交时间；多副本注意）
3. 选择验证对象（优先基线干净的对象；记录基线快照）
4. 执行验证（传与基线不同的值；观察状态码+回读值）
5. 判定（按规则 2/3 的判据表；500 必须查日志定位）
6. 恢复环境（配置恢复+回读确认；无法恢复立即告知）
7. 更新交付物（Excel 标注+报告结论+误判修正透明记录）
```

## 校验清单

- [ ] 修复提交 diff 已阅读，能说出改了什么、覆盖哪些路径
- [ ] 环境版本与部署时间已确认晚于修复提交
- [ ] 验证对象基线已知且最好为"无配置"状态（快照留存）
- [ ] 验证用了与基线不同的传入值，判定基于传入值与回读值对比
- [ ] 500 结果已查日志定位异常环节（排除"未走到修复代码"假象）
- [ ] 多副本环境确认请求实际落在哪个实例（或逐实例验证）
- [ ] 环境已恢复且回读确认
- [ ] 误判修正（如有）已透明记录

## 错误与异常处理

| 情况 | 处理 |
|---|---|
| 修复提交存在但环境版本较旧 | 判"未部署"，等部署后复测；期间可交叉环境验证 |
| 复测请求 500 | 查日志堆栈定位异常环节，确认是否前置失败（如外部依赖/数据问题）掩盖修复行为；换可达对象重验 |
| 回读与传入不一致但与基线一致 | 修复生效（写入被拦截）；同时确认基线残留不影响其他用例 |
| 两环境复测结果矛盾 | 优先检查两环境基线差异（规则 2 陷阱）；仍矛盾则逐环境确认部署版本 |

## 安全边界

- 复测改动（负值写入/非法配置）必须恢复基线并回读确认
- 共享环境的其他用户残留配置**不擅自清理**（可能他人正在使用）；仅恢复自己造成的改动
- 误判修正只改自己产出的结论，他人结论另行沟通
- 凭证不进入复测记录
- 在任何写入前记录目标、基线、风险级别、恢复步骤和证据位置；环境规则不允许的操作不因“复测”而获得授权

## 示例

**正例：总带宽负值复测**
- 基线 total=10 → PUT total=-1 → 200 + 回读 -1.0 → **未修复**（非法值入库）

**修复生效判定：编辑接口写高优**
- 对象基线 masterSwitch=false → PUT masterSwitch=true → 200 + 回读仍 false（=基线）→ **修复生效**（未写入）

**陷阱例：基线残留误判**
- 对象基线 masterSwitch=true（此前残留）→ PUT masterSwitch=true/scan=false → 回读 true/**true**（scan 回读=基线值而非传入 false）→ PUT 未生效，"写入成功"为残留假象

**500 假象例**
- PUT 编辑远程仓库带某配置 → 500 → 日志显示异常在"密级校验拉取远程 URL 返回 HTML"环节 → 请求未走到目标写入逻辑 → 500 的"未写入"不能证明修复，换 URL 可达对象重验

## 禁止事项

- 禁止以"回读值非空"判定写入发生（基线残留陷阱）
- 禁止把 500 当作修复证据（必须查日志定位）
- 禁止跳过代码 diff 确认直接环境验证（无法区分"未修复"与"未部署"）
- 禁止悄悄修改此前误判的结论而不留修正记录
- 禁止复测后不恢复基线
